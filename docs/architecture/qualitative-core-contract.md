# Qualitative Core Architecture Contract

Status: Accepted baseline for Phase 1 implementation

Date: 2026-07-28

## Purpose

This contract gives codebooks, cases, attributes, future coding references, memos,
saved queries, and reviewer decisions one durable project boundary. It establishes
the decisions that contributors must share before the manual qualitative
workbench is implemented.

The schema is an implementation foundation, not a claim that the Phase 1 or Phase
2 exit gates are complete. Codebook and case services, researcher-facing controls,
manual coding, search, reliability, and domain validation remain open work.

## Authoritative Storage Boundary

Each study owns one qualitative database:

```text
local_data/studies/<project_id>/qualitative.sqlite3
```

`project_id` is the existing study workspace ID. A second project identity must
not be invented.

This placement is intentional:

- all accepted qualitative metadata for a study shares one SQLite transaction
  boundary;
- codebook, case, coding, memo, query, and decision tables can use real relational
  constraints;
- the existing project archive automatically includes the database because it
  already archives every regular file under the study directory;
- restoring a study restores the exact qualitative database and migration ledger;
- unrelated studies remain separate files and can be backed up independently.

The database does not store original source blobs, transcript text, metric CSVs,
agent-job artifacts, or model credentials. Those remain in their existing stores.

## Baseline Schema

Migration 1 reserves the shared entities and relationships needed by the first two
contributor slices.

| Area | Tables | Responsibility |
|---|---|---|
| Project identity | `qualitative_projects`, `researchers` | Bind accepted changes to the existing study and a named actor. |
| Codebooks | `codebooks`, `codebook_versions`, `codes` | Hierarchy, definitions, stable cross-version keys, drafts, and frozen versions. |
| Cases | `cases`, `attribute_definitions`, `case_attribute_values` | Participants and other case kinds with typed project-defined attributes. |
| Evidence links | `source_case_links` | Associate a case with an existing project source without copying evidence records. |
| Provenance | `qualitative_audit_events` | Record accepted qualitative mutations in the same transaction as the mutation. |

Future migrations may add coding references, excerpts, memos, annotations, saved
queries, agent proposals, reviewer decisions, and exports. They must extend this
database rather than create parallel qualitative databases.

## Identifier Rules

- Existing study IDs remain the project IDs.
- Existing `project_source_id`, transcript-revision, passage, and C-unit IDs remain
  authoritative evidence references.
- Mutable research entities use random stable IDs generated by
  `new_qualitative_id`.
- A code has a version-local `code_id` and a `stable_code_key`. The stable key is
  carried into a later codebook version when the researcher intends the code to
  represent the same concept.
- File paths, display labels, list positions, and timestamps are never identities.
- IDs are never silently reused for different content or project ownership.

## Evidence Boundary

SQLite cannot enforce a relational constraint across `qualitative.sqlite3` and
the root-level `evidence.sqlite3`. A source-to-case write therefore has two gates:

1. Read the source through `EvidenceCatalog.source_history` and confirm that its
   `workspace_id` equals the qualitative `project_id`.
2. Insert the `source_case_links` row and its audit event in one qualitative
   transaction.

The qualitative database stores the stable source ID only. It must not copy
transcript content, source hashes, or revision lineage into the link table.

## Researcher Provenance

Accepted qualitative mutations require an explicit `researcher_id`. Do not add a
silent default such as `local-user`, `local-system`, or `anonymous`.

`QualitativeProjectDatabase.initialize` creates the project binding, first named
researcher, and deterministic initialization audit event. Repeating the exact
initialization is safe. Reusing the same researcher ID with a different identity
fails visibly.

Every later create, update, freeze, import, link, or value-setting operation must:

1. verify the actor is active and belongs to the project;
2. perform the domain mutation and append its `qualitative_audit_events` row in the
   same `QualitativeProjectDatabase.transaction` block;
3. record identifiers and non-sensitive change metadata, not transcript content;
4. roll back both writes if either write fails.

The audit table is append-only. Authentication and cryptographic audit integrity
remain Phase 6 work and must not be claimed by these slices.

## Mutation And Versioning Rules

- Cases and attribute values are mutable records. Every update changes
  `updated_by` and `updated_at` and appends an audit event.
- Codebook versions are mutable only while `status = 'draft'`.
- Freezing a codebook version is one-way. Database triggers reject later inserts,
  updates, or deletes against its codes and reject updates or deletion of the
  frozen version row.
- A revision after freeze creates a new draft version linked through
  `based_on_version_id`; it does not unfreeze or overwrite the prior version.
- Code hierarchy cycles and typed attribute values require service-level
  validation because simple relational constraints cannot express those rules.
- Destructive project lifecycle and retained-data deletion remain separate roadmap
  work. Contributors must not add cascade deletion around that decision.

## Transaction And Migration Rules

- Use `QualitativeProjectDatabase.transaction` for accepted writes. It enables
  foreign-key enforcement and starts `BEGIN IMMEDIATE` before yielding.
- Do not open this database through ad hoc `sqlite3.connect` calls in application
  services.
- Migrations use the existing `apply_migrations` ledger and must be contiguous,
  named, forward-only, and transactional.
- Do not use `sqlite3.executescript` inside a migration because it implicitly
  commits. The baseline executes complete statements without breaking the
  migration transaction.
- Never edit an applied migration. Add the next migration after rebasing onto the
  latest `master`.
- Two schema-changing branches may be developed concurrently, but the second PR to
  merge must rebase and renumber its migration if the first PR claimed that
  version.
- A database newer than the running application is refused rather than guessed at.

## API And Module Boundaries

- Shared database and identifier behavior stays in
  `backend/qualitative/database.py`.
- Codebook behavior belongs in `backend/qualitative/codebooks.py`.
- Case and attribute behavior belongs in `backend/qualitative/cases.py`.
- HTTP request validation and response mapping stay in the FastAPI layer.
- Storage services accept plain typed values and return domain records; they do
  not import FastAPI models or raise HTTP exceptions.
- The initial status contract is
  `GET /api/studies/{study_id}/qualitative/schema-status`.
- API errors must distinguish missing records, validation failures, immutable
  state, and schema incompatibility. Do not catch broad exceptions and report
  success.

## Merge And Ownership Rules

Rahfay owns the first codebook service slice. Mark owns the first case and typed
attribute service slice. Their assignment packets define exact scope and proof.

The work may proceed concurrently after this checkpoint reaches `master`.
Neither slice may change the other slice's tables or service module without a
reviewed contract change. If both branches need a new migration, merge one, rebase
the other, and preserve one linear migration history.

Manual coding is deliberately the next integration slice. It should not begin
until both foundations expose stable, tested operations because a coding reference
must join exact evidence, a codebook version, a code, a researcher, and eventually
a case without duplicating any of them.

## Known Limits

- The schema does not make the current JSON `StudySchema` obsolete. Mark's task
  must document compatibility and migration behavior before replacing it.
- External source ownership is checked by the application because SQLite cannot
  enforce constraints across database files.
- The baseline has no codebook or case CRUD API and no UI. Those are the assigned
  implementation slices.
- Local single-user identity is represented, but Windows identity and role-based
  authorization are not implemented.
- The audit table is append-only but is not authenticated or cryptographically
  chained.
- No real or sensitive research data is authorized by this checkpoint.
